## ۱. نمای کلی

UTMS سامانه مدیریت درخواست تست، نیازمندی، سناریو و تست‌کیس، اجرای تست،
خطا، بازآزمایی، کنترل کیفیت، بررسی امنیت و تصمیم انتشار است.

اجزای اصلی سامانه:

- رابط کاربری React 19 و Vite 7 در `apps/web`
- API مبتنی بر Node.js و Domain RPC در `apps/api`
- PostgreSQL 16 و Prisma 7 در `database`
- Nginx و Docker Compose برای اجرای یکپارچه محیط

## ۲. نقش‌ها و مسیرها

نقش‌های فعلی سامانه عبارت‌اند از مدیر سامانه، برنامه‌نویس، سرپرست QA،
متخصص QA، تحلیل‌گر کسب‌وکار، کارشناس امنیت، سرپرست فنی و مالک محصول.
دسترسی به صفحه‌ها براساس نقش کنترل می‌شود.

| حوزه | مسیر |
|---|---|
| داشبورد | `/dashboard` |
| درخواست‌های تست | `/test-requests` |
| نیازمندی‌ها | `/requirements` |
| تست‌کیس‌ها | `/test-cases` |
| اجراها و خطاها | `/test-runs-bugs` |
| کارتابل برنامه‌نویس | `/developer-board` |
| مشکلات اجرای تست | `/run-issues` |
| چک‌لیست امنیت | `/checklists` |
| بررسی امنیت و رفع موارد | `/security-review` |
| مدیریت انتشار | `/releases` |
| گزارش‌ها | `/reports` |
| کنسول API | `/api-console` |

## ۳. گردش‌کار درخواست تست

برنامه‌نویس درخواست را با اطلاعات سامانه، نسخه، شماره Build در صورت وجود،
محیط، اولویت، ریسک و یک یا چند نوع تست ایجاد می‌کند.

انواع تست ذخیره‌شونده عبارت‌اند از تست اولیه (`INITIAL`)،
بازآزمایی/رگرسیون (`RETEST_REGRESSION`)، تست دود (`SMOKE`)، پذیرش کاربر
(`UAT`) و اکتشافی (`EXPLORATORY`). مقادیر فنی مانند `INITIAL` در رابط
کاربری به فارسی نمایش داده می‌شوند.

وضعیت‌های اصلی درخواست شامل پیش‌نویس، ثبت‌شده، در حال بررسی،
پذیرفته‌شده، ردشده، لغوشده، در حال انجام و تکمیل‌شده است.

### ارجاع به متخصص QA

هنگام ارجاع درخواست:

- نام فرد گیرنده در تاریخچه درخواست ثبت و نمایش داده می‌شود.
- برای متخصص QA اعلان داخل سامانه ایجاد می‌شود.
- درخواست در کارتابل متخصص مربوطه قابل مشاهده است.

شماره Build هنگام ایجاد درخواست می‌تواند خالی باشد. اگر برنامه‌نویس آن را
وارد نکرده باشد، سرپرست QA می‌تواند پیش از ثبت وضعیت کیفیت آن را تکمیل کند.

## ۴. نیازمندی، جریان و تست‌کیس

ساختار اصلی داده‌ها:

```text
Application
└── Test Request
    └── Requirement
        └── Flow
            └── Test Case
```

درخواست تست، نیازمندی، جریان و تست‌کیس در PostgreSQL ذخیره می‌شوند. فهرست
آن‌ها هنگام دریافت از سرور تازه‌سازی می‌شود؛ بنابراین با Refresh مرورگر یا
دکمه تازه‌سازی از بین نمی‌روند.

## ۵. اجرا، خطا و بازآزمایی

متخصص QA برای تست‌کیس‌ها اجرا ثبت می‌کند. وضعیت‌های اجرا شامل باز، موفق،
ناموفق، مسدود و نادیده است. اجرای نهایی مبنای محاسبات کنترل کیفیت و خلاصه
درخواست است.

خطاها می‌توانند شدت‌هایی مانند Blocker و Critical داشته باشند. خطاهای
ارجاع‌شده به برنامه‌نویس در کارتابل او پیگیری می‌شوند و پس از رفع، بازآزمایی
توسط QA انجام می‌شود.

## ۶. ثبت وضعیت کیفیت توسط سرپرست QA

سرپرست QA در کارتابل «ثبت وضعیت کیفیت» یکی از وضعیت‌های آماده، آماده
مشروط، آماده نیست یا احتیاج به اجرای مجدد را ثبت می‌کند. ثبت وضعیت کیفیت
نیازمند وجود نسخه مرتبط است.

در وضعیت «احتیاج به اجرای مجدد»، درج دلیل اجباری است. با انتخاب آن:

- درخواست دوباره در وضعیت «در حال انجام» قرار می‌گیرد.
- دلیل سرپرست QA برای متخصص QA نمایش داده می‌شود.
- برای متخصص QA اعلان داخل سامانه ارسال می‌شود.
- کارت در بخش «درخواست‌های نیازمند اجرای مجدد» قابل مشاهده می‌ماند.
- متخصص QA باید یک اجرای نهایی جدید ثبت کند.

بعد از ثبت اجرای نهایی جدید، وضعیت کنترل کیفیت به «در حال بررسی» منتقل
می‌شود، کارت از فهرست نیازمند اجرای مجدد خارج می‌شود و سرپرست QA برای بررسی
دوباره مطلع می‌شود.

## ۷. درخواست تست امنیت

گزینه «احتیاج به تست امنیت دارد» فقط هنگام انتخاب وضعیت «آماده» یا «آماده
مشروط» توسط سرپرست QA قابل انتخاب است.

- بدون انتخاب گزینه، درخواست به کارتابل کارشناس امنیت نمی‌رود.
- با انتخاب آن، اطلاعات امنیت و چک‌لیست اجباری می‌شوند.
- بررسی امنیت برای هر **درخواست تست** ایجاد می‌شود، نه برای هر تست‌کیس.
- برای هر درخواست فقط یک بررسی امنیت فعال ایجاد می‌شود.
- برای کارشناس امنیت اعلان داخل سامانه ارسال می‌شود.

### اطلاعات درخواست تست امنیت

سرپرست QA باید نوع سامانه، Frontend، Gateway، Backend، Database،
Web Server / Reverse Proxy، مدل ارتباط، نوع و روش اصلی تست، محیط، URL اصلی
و فرعی، وضعیت دسترسی، نیاز به VPN و IP Whitelist، ساعات مجاز، تاریخ شروع و
پایان دسترسی، پایداری محیط، مسئول پشتیبانی و تماس اضطراری را تکمیل کند.

هرجا دامنه مشخصی وجود دارد، مقدار از فهرست انتخاب می‌شود؛ از جمله نوع
سامانه، فناوری‌ها، مدل ارتباط، نوع تست، محیط، وضعیت دسترسی و پایداری.

### احراز هویت محیط Development

اطلاعات شامل URL محیط، روش و شناسه ورود، حداقل یک حساب برای نقش‌های مهم،
نقش حساب‌ها، تاریخ انقضا در صورت وجود، روش امن تحویل رمز، امکان Reset و
مسئول Reset در صورت فعال بودن آن است. **رمز عبور نباید داخل فرم نوشته شود.**

### احراز هویت محیط Test

اطلاعات شامل URL، نام و پروتکل SSO Provider، حساب‌های تست SSO، نقش‌ها،
Tenant، وضعیت MFA، Callback و Redirect Domain، مدت Session، رفتار Logout،
تاریخ انقضا و محدودیت شناخته‌شده SSO است. بدون حساب تست SSO، شروع بررسی
امنیت محیط Test مجاز نیست.

### اطلاعات محیط Production

تست Production فقط با مجوزهای صریح انجام می‌شود. حساب کنترل‌شده، مالک و
نقش حساب، مجوز مالک کسب‌وکار، مسئول فنی، مالک Production و تیم امنیت، بازه
مجاز، تماس اضطراری، تأیید Monitoring و Backup/Rollback، محدودیت اسکن،
تغییر و حذف داده و شرط توقف تست باید مشخص شوند.

### تاریخ‌ها

همه ورودی‌های تاریخ و تاریخ‌وساعت در رابط کاربری به‌صورت شمسی هستند.
هنگام ذخیره، مقدار سازگار با API تولید می‌شود و نمایش مجدد برای کاربر به
تقویم شمسی برمی‌گردد.

## ۸. کارتابل کارشناس امنیت

کارت بررسی امنیت خلاصه شواهد درخواست را نشان می‌دهد:

- نام سامانه، نیازمندی/تست‌کیس، نسخه و Build
- نوع و تاریخ درخواست برنامه‌نویس
- سرپرست فنی، برنامه‌نویس، متخصص QA و سرپرست QA
- تاریخ تأیید سرپرست
- تعداد تست‌کیس‌ها و جزئیات قابل مشاهده
- اجراهای نهایی، باز، موفق، ناموفق، مسدود و نادیده
- خطاهای باز Blocker و Critical

کارشناس امنیت نتیجه همه اقلام را با یکی از مقادیر قبول، رد، ناقص یا
غیرقابل اعمال ثبت می‌کند. گزینه «تست نشده» در بررسی امنیت وجود ندارد.
تکمیل بررسی فقط وقتی مجاز است که همه اقلام نتیجه داشته باشند و حداقل یک
مستند امنیت نیز بارگذاری شده باشد. سقف هر فایل ۱۰ مگابایت است و فایل
ذخیره‌شده در مراحل بعدی برای نقش‌های مجاز قابل دانلود است.

پرونده تکمیل‌شده از فهرست چک‌لیست حذف نمی‌شود و فقط وضعیت آن تغییر می‌کند.
اگر همه نتایج «قبول» یا «غیرقابل اعمال» باشند، مرحله نسخه به «در انتظار
تصمیم» منتقل و برای سرپرست فنی اعلان ایجاد می‌شود.

اگر حداقل یک نتیجه «رد» یا «ناقص» باشد، پرونده همراه تمام نتایج و مستندات
به کارتابل «بررسی امنیت» سرپرست QA می‌رود:

1. سرپرست QA با توضیح اجباری پرونده را به متخصص QA ارجاع می‌دهد یا برای
   اصلاح به تیم امنیت بازمی‌گرداند.
2. متخصص QA یک «اجرای امنیتی» تعریف و آن را به برنامه‌نویس ارجاع می‌دهد.
3. برنامه‌نویس شرح رفع مشکلات را ثبت می‌کند.
4. متخصص QA گزارش حداکثر ۱۰ مگابایتی را بارگذاری و برای سرپرست QA می‌فرستد.
5. سرپرست QA گزارش را تأیید و به تیم امنیت برمی‌گرداند یا برای اصلاح به
   متخصص QA بازمی‌گرداند.
6. تیم امنیت نتایج را دوباره بررسی می‌کند. نتیجه نهایی قبول/غیرقابل اعمال
   به سرپرست فنی می‌رود و نتیجه دارای رد/ناقص دوباره وارد همین چرخه می‌شود.

همه انتقال‌ها با اقدام‌کننده، زمان، وضعیت مبدأ و مقصد، توضیح و شناسه
فایل‌های مرتبط در تاریخچه پرونده قابل ردیابی هستند. کارتابل بررسی امنیت
برای مدیر سامانه، سرپرست QA، متخصص QA، برنامه‌نویس و کارشناس امنیت قابل
مشاهده است؛ هر نقش فقط اقدام مرحله مربوط به خود را می‌بیند.

## ۹. تصمیم انتشار

سرپرست فنی یا نقش مجاز طبق سیاست گردش‌کار، تصمیم تأیید، تأیید مشروط، رد یا
مسدود را ثبت می‌کند. در تأیید و تأیید مشروط، درخواست اصلی نیز به وضعیت
«تکمیل‌شده» منتقل و تغییر با منبع تصمیم انتشار در تاریخچه ثبت می‌شود؛
بنابراین ستون وضعیت کارتابل نباید «در حال انجام» باقی بماند.

## ۱۰. تاریخچه

تاریخچه، عملیات مهم مانند ایجاد، ثبت، ارجاع، تغییر وضعیت، کنترل کیفیت و
تصمیم انتشار را نشان می‌دهد. مقادیر فنی در رابط کاربری ترجمه می‌شوند:

- `STATUS_CHANGE` ← تغییر وضعیت
- `ASSIGN` ← ارجاع
- `INITIAL` ← تست اولیه

در رویداد ارجاع، گیرنده ارجاع نیز نمایش داده می‌شود.

## ۱۱. مرز فعلی ذخیره‌سازی

| داده | وضعیت فعلی |
|---|---|
| کاربران، اعتبارنامه‌ها و نقش‌ها | PostgreSQL از طریق Prisma |
| سامانه‌ها | PostgreSQL از طریق Prisma |
| سیاست‌های گردش‌کار | PostgreSQL از طریق Prisma |
| درخواست، نیازمندی، جریان و تست‌کیس | PostgreSQL از طریق پل مدیریت تست |
| اجرا، خطا، بازآزمایی، مشکل اجرا و نسخه | وضعیت انتقالی فایل/حافظه |
| بررسی امنیت، اعلان، ممیزی و پیوست | وضعیت انتقالی فایل/حافظه |

پل مدیریت تست پیش از خواندن، داده را از PostgreSQL تازه می‌کند و پس از
عملیات تغییردهنده، چهار مجموعه درخواست، نیازمندی، جریان و تست‌کیس را در یک
تراکنش ذخیره می‌کند.

## ۱۲. API و حالت جایگزین کلاینت

رابط کاربری عملیات را به `/api/domain/rpc` ارسال می‌کند. حالت جایگزین محلی
فقط برای سرویس‌های مجاز و خطاهای دسترس‌پذیری مانند قطع ارتباط یا پاسخ‌های
502، 503 و 504 فعال می‌شود. خطاهای اعتبارسنجی و دامنه به حالت محلی منتقل
نمی‌شوند.

سرویس‌های کاربر، سامانه و سیاست گردش‌کار فقط از Backend خوانده می‌شوند و
حالت جایگزین محلی ندارند.

## ۱۳. راه‌اندازی و کنترل

پیش‌نیازها Node.js 22، npm و PostgreSQL 16 یا Docker Desktop هستند.

```bash
npm ci
npm run db:migrate
npm run db:seed
npm run dev:all
```

نشانی رابط کاربری `http://localhost:5173` و API برابر
`http://localhost:4174` است.

کنترل کامل مخزن:

```bash
npm run verify
```

## ۱۴. محدودیت‌های شناخته‌شده

- مهاجرت همه دامنه‌ها به PostgreSQL کامل نشده است.
- `VersionHistory` هنوز دامنه مستقل PostgreSQL نیست؛ فیلدهای کنترل کیفیت،
  امنیت و تصمیم انتشار روی snapshot درخواست نیز نگهداری می‌شوند.
- داده‌های انتقالی فایل/حافظه برای اجرای چند نمونه هم‌زمان API مناسب نیستند
  و باید در ادامه به ذخیره‌سازی مشترک منتقل شوند.

## ۱۵. مسیرهای مرجع در سورس

- مسیرهای رابط کاربری: `apps/web/src/App.tsx`
- نقش‌ها و مدل‌های دامنه: `apps/web/src/types/index.ts`
- کنترل دسترسی: `apps/web/src/stores/authStore.ts`
- API دامنه کلاینت: `apps/web/src/services/api.ts`
- کلاینت Domain RPC: `apps/web/src/services/domainRpcClient.ts`
- عملیات دامنه: `apps/api/src/modules/domain-rpc/domain-rpc-service.cjs`
- پل PostgreSQL:
  `apps/api/src/modules/domain-rpc/postgres-test-management-state.cjs`
- مدل Prisma: `database/prisma/schema.prisma`
- مهاجرت‌ها: `database/prisma/migrations`
